## Learning candidate
**Clock injection beats time-travel helpers when Redis holds the timestamps.**
`travel_to` freezes Ruby's clock but not the values already written into Redis sorted
sets, so window math desyncs and specs flake. Injecting a clock at construction and using
it for BOTH the write timestamp and the prune cutoff keeps app and store in the same
timeline. Verified here (flaky burst spec → deterministic, 40ms). Reusable for anything
window-based backed by an external store — the webhook backoff work (HW-102) will hit
this exact shape.
