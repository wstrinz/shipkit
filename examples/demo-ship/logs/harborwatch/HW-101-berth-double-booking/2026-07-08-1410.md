# HW-101-berth-double-booking - 2026-07-08-1410

**Ticket:** [HW-101-berth-double-booking](../../../projects/harborwatch/tickets/HW-101-berth-double-booking.md)

## Did
- Read the June 21 / July 2 incident notes; confirmed both were races (two front-desk
  sessions booked the same berth ~200ms apart) — the availability check passed for both
  because neither insert had landed yet. Anything that checks-then-inserts keeps that
  window open.
- Evaluated an app-level advisory lock vs a Postgres exclusion constraint. Recommended
  **the constraint** (`EXCLUDE USING gist` on berth + stay range): the lock only works if
  every write path remembers to take it (the two incident writes came through *different*
  paths), and check-then-insert is exactly the failure mode from the incidents. The DB
  enforcing the invariant also covers write paths that don't exist yet. ~40 lines + a
  migration.
- Wrote migration `migrations/0042_berth_stay_exclusion.py`: adds the constraint on
  `reservations` with `stay` as a half-open range, so checkout == next check-in books
  cleanly.
- Mapped the constraint violation in the reservations API to a 409 carrying the
  conflicting reservation's id.
- Started specs: basic-overlap-rejected and different-berths-isolated written and passing.
